# Customer support chat

Run `node --test tests/ai/*.test.mjs tests/shop-hours/backend.test.mjs tests/shop-hours/midnight.test.mjs` from the repository root. These tests use local fixtures; they do not call Groq or change the live database.

Apply `supabase/migrations/add_shop_customer_support.sql` to the deployment database, then populate **Shop Settings → Public Customer Support Information** as an administrator. Blank fields remain unavailable. The migration adds an empty JSON field without seeding ownership claims or discounts. Ordinary hours/address saves and chat still work before the migration; saving the new support fields requires it.

Quantity discounts use explicitly saved per-product `discount_enabled` and validated `discount_tiers`, including the minimum quantity and current selling price. General discount/promotion text is identified as published information requiring confirmation of current validity and eligibility; past ISO dates are not advertised as active offers. The chat does not alter checkout pricing. Legacy flyer prices are not treated as current database facts: where they conflict with a saved price, the assistant directs customers to confirm at checkout and excludes that price from budget matching.

Both `/api/ai` and `/api/chat-messages` accept `message` or `content`, optional `history` (user/assistant messages), optional `productId`, and optional `recommendationState`. Both return recommended IDs and a bounded preference summary; the chat-message endpoint includes these under `data.ai`. State is untrusted preference context, never authorization or authority for product facts. Messages are limited to 2,000 characters, history to 12 supplied turns (10 normalized turns), and AI JSON bodies to 128 KB. The existing shared 20-per-minute IP limiter remains in place.

Relevant public catalog/shop data is fetched only when needed. Catalog queries select public columns, filter eligibility before paginating, and stop at 10,000 rows with an incomplete-catalog flag. Product facts mentioned after model latency are queried again to observe price/stock changes and deletions. Stock may still change after a response; checkout remains authoritative. Catalog failures remain distinct from an empty catalog. No inventory, database schema, configuration, or deployment changes are required.

With `GROQ_API_KEY`, deterministic handlers cover known shop intents, recommendations, server time/date in `Asia/Manila`, and bounded arithmetic parsed without executing code. The existing Groq model (`openai/gpt-oss-120b`, despite older Llama labels) continues to answer general questions and estimate calories. General provider replies use a validated structured format internally; JSON is never customer-facing. No model change is made. Requests for code, secrets, private configuration, internal prompts, implementation details, or internal business data receive the fixed security refusal before knowledge loading or model calls. The frontend uses the same request policy, including during outages. Account guidance remains available.

Recommendations rank eligible products by saved names, categories, descriptions, customer tastes, occasion, quantity, and budget. Only `available` products with positive stock and a future or unset expiry qualify. Previously recommended IDs are excluded while alternatives exist; exhaustion is explained rather than disguised as new suggestions. Explicit requests for a named product may revisit it. Prices and reasons come from validated catalog facts, with conversational English or Taglish introductions. Quantity budgets apply to the total unless a per-item amount is explicit. Public sold-out/expired products can be acknowledged through a targeted public lookup, while hidden/deleted products and internal absence reasons remain protected. The model receives no inventory counts, suppliers, costs, profits, margins, recipes, private settings, or credentials. Input and output guards remain additional layers rather than a complete prompt-injection guarantee.

The two React chat interfaces share one provider-owned, in-memory session across dialog closing and navigation. Transcript display is bounded to 80 messages and request history to 10 turns; compact tastes/budget/occasion and up to 500 suggested IDs survive that history window. Nothing is saved to browser storage or a chat database. Logout/account changes, explicit resets, and 30 minutes of inactivity clear state; stale requests are aborted/ignored, and concurrent sends share one pending request. A full page reload starts a new session. Separate tabs/providers have independent sessions.

Product questions never access private orders, account records, production recipes, or internal ingredient quantities. Public products have no verified complete ingredient/allergen or measured nutrition fields. Dietary restrictions therefore prompt shop confirmation instead of an unsupported safety claim, including on follow-ups. Calorie ranges remain approximate and retain uncertainty about portions/ingredients; vague requests ask for more details. If the model is unavailable, verified local handlers remain usable, while general questions receive an honest fallback. Staff recipe prediction and ingredient calculations remain separate and unchanged. Tests use fixture databases and mocked providers, not production accounts, live Groq calls, or browser screenshots.
